What the `e2e_aarch64_globals_linux` log shows:

- every trust-cg object's `.rela.tdata` rows as GNU readelf prints them
  (`g_target + 0`, `tls_fn + 0`, `g_arr + 10`: addends in hex) with their
  offsets, the same rows as a gcc twin and as the gcc-compiled C oracle
  (`static __thread void *volatile p = &x;`; `volatile` because gcc -O2
  otherwise folds a never-written static template into constants), and the
  object's sha256;
- 8 trust-ir-route executions (static and PIE links), 4 `dlopen`ed TLSDESC
  shared-object executions with a thread that predates the `dlopen`, and 16
  Pipeline-route executions (local-exec and initial-exec, static and PIE),
  each comparing every thread's template with the C oracle;
- the negative controls: with the last `.rela.tdata` record dropped by a
  byte mutation the readelf row check and the driver (`main: template slot
  2: cg=(nil)`) both reject the object at every level, and a deliberately
  non-TLS twin module fails the driver's isolation check (a
  driver-sensitivity control, not a compiler negative);
- the JIT data image, a body `SymbolAddr` addend and the hidden/retained data
  attribute rows passing on Linux.

Boundaries. This is execution and object evidence for these programs on
this host, not proof of the linker, glibc's TLS runtime or the JIT. The
"O0-O3" grid is smaller than it looks: the trust-ir-route `static` and `pie`
objects of this small module are byte-identical at every level (one object,
two link modes), the `pic` objects take two distinct forms (O0/O1 and
O2/O3), and the Pipeline-route local-exec object is identical at every
level; the sha256 lines show which. The relocation inventory row names only
the `S + A` value written into the template. The certified `Compiler` route
(`emit_proofs`) still refuses these modules at proof promotion for unrelated
opcode coverage (`StpPreIndex`/`LdpPostIndex`, and the TLSDESC opcodes under
`pic`), so its artifact-digest cross-check was not reached with a TLS
template; the Pipeline inventory API count is what is tested. Objects and
binaries are not retained (they are regenerated by the commands above; their
sha256 are in the log). The Darwin floor target `e2e_aarch64_globals_darwin`
was edited on this host and type-checked here through a temporary
cfg-stripped copy; it has not run on macOS. The full 145-target Linux floor
was not rerun for this commit.
